## isolation level   [OK]
how:     same claim test at stricter levels. Real code at READ COMMITTED: see 'double claim'. Postgres default is READ COMMITTED; our safety comes from single conditional statements + row locks, not from the isolation level
real:    safe  (real claim at REPEATABLE READ: {'claims': 2000, 'jobs': 2000, 'claimed_twice': 0, 'errors': {'serialization_failure': 1536}})
note:    naive SELECT-then-UPDATE at SERIALIZABLE: {'claims': 2000, 'jobs': 2000, 'claimed_twice': 0, 'errors': {'serialization_failure': 15775}}
         -> at READ COMMITTED the naive code double-claims SILENTLY; at SERIALIZABLE the same
            bug turns into LOUD serialization errors. Our real claim is correct at READ COMMITTED,
            but at REPEATABLE READ it throws serialization errors under contention, which the
            worker does not retry (it would crash and be restarted). So: we depend on READ
            COMMITTED for availability, not for correctness.
